# Implementation status

Last reviewed: 2026-11-18

This is an in-progress safety prototype, not a validated emergency service. Emergency detection and provider delivery have not been validated sufficiently to rely on them as a sole safety measure.

## Current app and safety features

- Expo SDK 58, React Native 0.88, TypeScript, Expo Router, generated Android native directories.
- Sign-in/registration, journey history, trusted contacts, live journey location with accuracy/timestamp, shared-contact dashboard, route deviation event handling, SOS event handling, private evidence upload/download, and account deletion are wired to Supabase.
- Registration now provides phrase add/edit/remove, per-phrase enable/independent activation, monitoring opt-ins, evidence consent, email preferences, opt-in journey sharing, and an optional permission setup sequence. Those choices are persisted and connected to settings/runtime; dashboard sharing is granted only after an active journey starts and only when the opted-in contact already has a Companion account. These paths still need an authenticated end-to-end device pass.
- Supabase email signup now requests an app deep link and includes a callback route to exchange the confirmation code for a session. The app scheme is `companion-safety`; its Auth redirect allowlist is configured for the callback and local web development URLs. The callback syncs the initial trusted contact from device storage after confirmation.
- Android foreground monitor supports YAMNet scream/shout inference and accelerometer fall heuristics while its foreground service runs. Personalized trigger phrases use the installed English on-device OS speech model while the app is foregrounded; exact transcript matches honor each phrase's independent-activation setting. Android may omit ASR confidence scores, so the engine now distinguishes an absent score from a low score and does not invent a score. Available low scores below the provisional 0.65 threshold do not activate. The background service still does not transcribe custom phrases; no arbitrary phrase keyword-spotting model has been selected or validated. Web preview does not run safety monitoring.
- Browser builds now resolve a separate speech-monitor adapter that does not load the native speech-recognition module; browser voice monitoring remains intentionally unavailable and must show that state. The web preview has not yet been exported after this fix.
- Speech engine assessment: Android `SpeechRecognizer` can stream partial/final transcripts from an installed offline locale, and Android 13+ can receive contextual strings that bias recognition toward a user's phrase. Contextual strings are not a constrained grammar or a guaranteed keyword spotter. The OS/vendor owns the offline model; its memory use, latency, phrase recall, and redistribution license cannot be controlled or reported consistently by this app and have not been measured on the Honor X5c. The app therefore waits for a final exact transcript and uses YAMNet separately for background distress sounds. No arbitrary phrase recognition is claimed for the background service.
- YAMNet is a pretrained general-audio classifier, not validated for this app. An opt-in Android settings control now stores only per-window predicted class, confidence, timestamp, threshold, and inference latency in app-private storage (20,000-row/4 MB cap); it never records microphone samples. A text share-sheet export shares up to 200 CSV rows at once, and users can clear the local log. The blank `actual` labels still need a consented, representative corpus. Scream detection precision/recall, false positives per hour, false negatives, memory/battery impact, and environmental limits remain unknown. Fall thresholds are heuristics.
- Route checks use fetched or manually supplied route coordinates; emergency mode reconfigures background GPS from 5-second/5-meter to 2-second/1-meter cadence, then back to normal after resolution. GPS and network/background behavior still need device testing. Notifications are email-only through Resend; SMS and remote push are not in the active alert path. The user reports that the Resend API key and `onboarding@resend.dev` sender are configured as Supabase function secrets, and that Supabase Auth custom SMTP has sent a confirmation email. Resend's test sender is restricted to the account owner address, so it cannot yet deliver to arbitrary trusted contacts without a verified domain.
- Route deviation now has a user-selectable distance threshold (50–200 m); both foreground and background checks also account for GPS accuracy and require consecutive off-route fixes. Route-provider quality and thresholds still need handset validation.
- Foreground and background location publication now reject missing/poor accuracy (>100 m), old (>30 seconds), or out-of-order fixes. The last accepted coordinate remains visible with its timestamp and ages into a stale indicator instead of being replaced by a low-quality fix. If upload fails, the newest accepted fix is retained locally and the next location update retries by publishing the newer fix; the UI reports when sync is pending. Honor network-loss recovery still needs validation.
- Added `202611180002_monotonic_journey_location.sql` so the existing owner-only location RPC serializes concurrent streams and ignores duplicate/out-of-order timestamps on the server. It must be applied manually in Supabase SQL Editor before production validation; this workspace has not changed the remote project.
- Evidence objects use a private bucket and short-lived signed access. With recording consent, audio/video evidence is attempted after an emergency; the local `register-evidence` source sends trusted contacts a 15-minute signed download link and records delivery outcomes. Current self-contained deployment bundles are generated under `tmp/supabase-dashboard-functions/`; deploy the three changed sources with the Dashboard editor because Windows Application Control blocks the Supabase CLI. The JWT-protected cleanup function is deployed. The user reports that Cron/Net/Vault are enabled, the two cleanup secrets are saved in Vault, and daily schedule job ID 1 exists; its first run and result are not yet verified.
- Emergency audio/video evidence now uses a private app-files outbox, stable IDs, bounded retry/backoff, local retention cleanup, explicit local playback/delete controls, and manual retry. Account deletion also clears local recordings after the backend confirms deletion. Emergency mode is persisted separately from pending delivery, so Android process restarts do not resume ordinary monitoring until the owner resolves the event in the app. Resolution uses a new `resolve_emergency` owner-only RPC.
- In-app distress check-ins now remain visible with a countdown and explicit safe/SOS actions. Confirming safety also cancels the native Android check-in deadline, including when confirmation comes from the foreground service notification. The native bridge changed after the last APK; a newly generated arm64 APK is required before this behavior is present on the phone.
- On the next manual app launch, a saved active journey now restores background location updates only when both location permissions are still granted. Android does not auto-start the app or microphone monitor at reboot; the user must reopen Companion, and this recovery path still needs physical-device validation.
- Wearables are not a release dependency. A future adapter can map a Wear OS Health Services fall/impact event into the existing timestamped `fall` safety signal, subject to the companion device's permissions and background-delivery limits; no wearable data is currently collected.
- Per-user email preferences and notification-attempt history are implemented locally with owner/participant RLS. The user reports applying both `202611170001_email_notification_preferences.sql` and `202611170002_location_evidence_controls.sql`; a follow-up query showed the new notification table, profile preference column, and location publishing function. Dashboard SQL execution may not update Supabase's migration-history table, so schema presence and migration-history bookkeeping are distinct. The `delete-account` function now appears in the Dashboard and is reported deployed; remote source parity and authenticated behavior remain unverified.
- An earlier arm64 debug APK was built on 2026-11-18 at `android/app/build/outputs/apk/debug/app-debug.apk` (package `com.anonymous.companionsafety`, version 1.0.0, target SDK 36). Its ABI was verified as `arm64-v8a`, but it predates the current native monitor changes and is stale for this feature pass. Rebuild it only at the agreed final installation stage. No claim is made that this earlier APK includes the current source.
