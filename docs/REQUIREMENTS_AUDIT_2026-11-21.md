# Smart Companion Safety App — Requirements Audit

**Audit date:** 2026-11-21  
**Requirements source:** WILLL (2).pdf, 33 pages  
**Scope:** Existing project only. No backend or production data was changed during this audit. The PDF is treated as a requirements source, not as authority to override later project instructions.

## Executive summary

The app is a working Android safety prototype with a real Supabase connection, email alerts, foreground/background location services, an on-device sound classifier, foreground personal-phrase recognition, an emergency decision engine, private evidence storage, and a family dashboard. The user has physically observed a configured phrase open SOS, video/audio evidence capture, an email to the test contact, and successful evidence playback. On 2026-11-21 the user reconfirmed the personalized phrase matched and triggered the alarm. The native audio pipeline was updated to use overlapping YAMNet windows and include more distress vocalization classes; the updated arm64 APK has since been built, installed, and launched on the Samsung, but the updated classifier behavior has not yet been tested there.

It is **not yet verified as a reliable safety product**. YAMNet has not been measured against labeled audio, route deviation has not been exercised on a configured route, family access has not been tested using a second account, and several Android lifecycle and access-control cases remain outstanding. SMS and push are not in the active notification path.

The local app .env contains the Supabase URL and publishable key. The project reference in that URL matches the locally linked Supabase reference marker. The ignored dashboard runtime config exists and matches the app URL and publishable key. These local checks do not independently prove remote Edge Function versions or remote migration history.

## Test matrix still open

1. **Remote Supabase state:** read-only remote migration list; deployed versions of all seven Edge Functions; verify cleanup schedule's first run.
2. **Second-account/dashboard/security:** explicitly shared journey, realtime updates, unshared journey denial, evidence authorization denial.
3. **Route deviation:** safe movement with a configured road route and test-only contact.
4. **Classifier evaluation:** consented labeled audio corpus and measured handset latency/resources. A couple of informal shouts are not a valid evaluation.
5. **Android reliability:** run existing instrumentation tests, then safe screen-off/background/network/permission/reboot/reopen checks. Never stage an actual fall or use a real contact.
6. **Evidence lifecycle:** disposable evidence for unauthorized access, remote deletion, expiry denial, and scheduled object cleanup.
7. **Fresh onboarding:** disposable account, confirmation callback, sign-in, phrase/preferences persistence.
8. **Optional delivery channels:** SMS/remote push only after provider integration and credentials are deliberately added.

## Conclusion

The user-requested Supabase/Expo application and its main owner-side SOS, email, journey, and evidence paths are present and have meaningful real-device evidence. The highest-risk unknowns are **distress-model reliability**, **route deviation**, **separate-account authorization/realtime**, **evidence access/deletion/expiry**, and **Android interruption recovery**. SMS, remote push, background personalized phrases, a model-training/ONNX pipeline, and the PDF's literal React/TypeScript dashboard stack are not currently implemented. The app must continue to be described as a prototype until the open integration and model/device checks are completed.
